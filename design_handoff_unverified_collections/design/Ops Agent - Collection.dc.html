A3Collecting with no signal — the third state

Unverified is a state of the proof, not of the money. The cash moved in the shop; that is settled the moment it changes hands and nothing in the product should pretend otherwise. What is outstanding is whether the four digits the owner read out were the right four digits — and the phone cannot know that until it reaches the network. So the line is collected and verification: queued at once, and the two never get collapsed into one word.

Signal is shown as a consequence, not a bar. AGT-13 never asks him to read a reception icon: each shop on the round carries what will happen there in words — codes checked here or codes checked later — decided from the last three visits, not the current bar count. The round works; a specific sentence changes.

He still asks for the code. Dropping it offline would be the easy design and it would be fatal — a code nobody ever asked for is a code that never existed. He types the digits, the phone stores them, and the confirm in AGT-15 replaces “there is no undo” with the sharper truth: this is still final — and I cannot check these four digits until I have signal. Irreversible and unverified are separate promises, both kept on the same screen.

The provisional receipt is honest without being an accusation. Dashed border, the word unchecked, a plain sentence about what happens when it syncs, and no red — red is for a failure, and he has not failed. AGT-16 gives him the number he actually wants: 3 unchecked · 4 120 DH, carried at the top of the round until it clears.

The sync landing is the real design. Match (AGT-17) is a quiet one-line settling — a badge turning plain, no celebration. Mismatch (AGT-18) has to work when he is thirty kilometres away with the cash in his bag, and it must not read as an accusation: the likeliest cause is a stale code on the owner’s screen. So it asks for the one thing only he has — what he saw — and does the rest by phone. Crucially the money is not reversed and the owner’s line is not silently altered: the collection stands, the proof is marked failed check, and the owner’s statement in AGT-19 changes from “waiting to be checked” to a direct question with his own money in it. He is never told a code confirmed something it did not.

On the run, queued is a third column. AGT-20 keeps 6 420 DH of week 36 visible as collected, unchecked right through release, so no one reconciles a week believing it is settled. Release is allowed — the money is real — but the number is on the release confirmation and in the closing pack.

How long may a collection stay unverified? The clock starts at the moment of collection, not at first sync attempt — otherwise an agent who never opens the app never starts it.
Under 12 hours: nothing. A normal offline round. Not surfaced anywhere but the agent’s own tally; no one is told, because a queue that pages someone every evening is a queue people learn to ignore.
At 24 hours: a queue item with an owner. It appears on the duty desk with the agent’s name and a one-tap make him sync push. Still routine — a dead phone, a day off. The owner sees nothing new; his line already says waiting to be checked.
At 72 hours, or the moment the week is released with it still queued: an incident, whichever comes first. It stops being a queue item because the failure is no longer plausibly technical: three days is longer than any round, and a released week is a number someone has already acted on. Told, in this order: the agent (a blocking screen — his next round will not load until his queue is empty), the Head of Ops by name on the Monday list, and Finance if a released run is affected. The owner is told at 72 hours too — his line reads “we still haven’t been able to check this” with the amount and the agent’s name, because at three days he has a right to know that money marked against him is resting on nobody’s word but the agent’s. And a code failing to match is never a queue item at any age: it is an incident the moment the check runs, straight to the duty desk.
Ceilings, so the queue cannot grow quietly: an agent may hold at most 5 unchecked collections or 6 000 DH of them. At the ceiling the app will not open another collect — he can hand over, and he can call ops for an authorisation, but he cannot keep stacking unchecked cash. New fields: verification: verified | queued | failed, code_captured_at, synced_at, queued_age_h, incident_ref. Nothing on this path touches a bank, a card, or a fee.

The code-fallback turn · A2
A2When the code will not come

The code in AGT-03 proves one specific thing: that the agent was standing in the shop with a consenting owner. So the failure case cannot be answered by loosening the code — it has to be answered by a different proof that is honestly labelled as different, everywhere it lands.

It is a ladder, not an error. Three rungs the agent can climb alone, in cost order — wrong screen, any other phone, ring the owner — and only then a call to ops. The first two rungs keep it code-verified, which is why they come first: they cost nothing and lose nothing.

A code read down the phone is refused on purpose. It is the tempting shortcut and it is the one thing that would quietly destroy the mechanism: it proves the owner agreed, not that the agent is in the shop, and once we accept it every code in the system means only the weaker of the two things. So rung 3 phones the owner and then routes into the ops call, where the conversation is captured, rather than pretending the digits arrived the normal way.

The friction is a number about himself, not a delay. A timer teaches agents to wait 90 seconds. His own rate next to the team’s (2 in 30 days · team 0.4) is on the screen before he taps, and he knows it is the number Karima sorts by. That is what stops it becoming the default without making it feel like punishment.

Ops does not authorise the agent — ops reaches the owner. In AGT-08 the duty person calls the number on file, asks the owner the amount first and the agent second, and the two numbers have to match on screen before anything can be issued. The owner is still the one vouching; ops is the channel and the witness. Only when the owner cannot be reached does the agent become the sole voucher — and that is a separate, visibly thinner grade with the owner’s confirmation still outstanding.

The receipt cannot be mistaken for a code one. Amber band, six digits not four, the duty officer’s name where the owner’s code used to be, and the same words on the owner’s statement in AGT-11 — a year later, anyone reading either statement can tell which kind of proof they are looking at.

Should an agent be able to leave without closing the visit? Yes — but only before the cash is in his hand. Forbidding it is worse than allowing it: an agent who cannot leave will invent a close, or stand in a shop arguing with a barber. So AGT-07 lets him walk, and makes walking a recorded act rather than a null one — a reason, his name, a time, and a line the owner sees (“Hicham came Friday 18:40 and could not close”), never a blank.
Four things stop it becoming the easy path. The money does not go away — day 6 of 14 keeps counting and the visit returns tomorrow at the top of his round, so abandoning buys a second trip, not relief. His rate is shown to him at the moment of tapping, against the team’s. The second abandon takes the shop off him — the third visit routes to another agent and ops phones the owner, so quitting twice loses him the round rather than shortening it. And holding cash removes the option entirely: the first question on the abandon sheet is whether he has counted money, and “yes” leads only to the ops call. Cash that has moved must be recorded before he is out of the door; that is the one place the product refuses him a way out.
New state on the line: verified_by: code | ops_call, with ops_call.owner_reached: bool, call_ref, duty_user, and a dispute_window that only exists when the owner was not reached. Plus visit_attempt (visit, agent, time, geo, reason, closed: false) — the abandon is a row, and two of them on one shop is the trigger in AGT-12. Still no bank, card or fee anywhere on this path.

The offline case · A3
A1The agent’s round — a settlement is not a float pickup

BCF-04 takes a float off a barber: one person, one amount, no counterparty who could disagree. This is a different act and it needed its own screens — a shop rather than a person, a number that can point either way, a partial that is normal rather than an error, and a piece of paper at the end.

Direction is the row’s first fact, not its colour. Collect and Hand over are words on every row and on every button, because the agent reads this list on a scooter in the sun and colour is the first thing that goes. Green and amber only reinforce.

The round is ordered by age, not by geography. The oldest uncollected dirham is what the 14-day promise is measured against (slice 2 §2.6), so day 9 sits above day 4 even if it is across town. Route optimisation would quietly re-sort the list against the only deadline the business has.

Hand-over rows have no age, and that is shown rather than faked. Age measures how long a shop has held our money. When we owe them, nothing of ours is late — so the row says how long they have been waiting instead. Same list, two different clocks, both named.

The bag is on the screen. He is walking around with cash and the amount is his personal risk, so it is stated at the top with its cap and its drop-off, split into what he has collected and what he is still carrying to give away. This is the number that makes him choose to go to the office before the last visit.

The confirm is a code, not a checkbox. AGT-03 is the immutable moment, so the friction is placed there and nowhere else: the owner reads out the 4-digit code his own app is showing, which is the same mechanism the shop side already uses. See the note below on what that does and does not prove.

Partial is the same path as full. One field, a keypad, and a Full amount chip. Typing less than the full number is not an error state — it changes one sentence on the screen, which tells him what happens to the rest, in words he can repeat to the owner.

Rejected: an undo. There is none, so the design does not imply one; instead the receipt screen says plainly that a mistake becomes a line on next week’s statement and links to the support case that starts it. Also rejected: a signature on the collect direction — asking a man who has just handed over his cash to sign for it is theatre, and it would let the real proof (his code) look optional.

What stops him recording a collection he didn’t make — both, on different directions. The 4-digit code survives, and it belongs to Collect: the owner reads it out of his app, it is tied to that visit and that amount, and it rotates. It proves the agent was standing in the shop with a consenting owner — which is exactly the fraud in that direction, an agent inventing a collection from his scooter. The signature cannot do that job, because a signature on the agent’s own phone is drawn by whoever is holding the phone.
On Hand over the code proves nothing worth having — the owner being present is not in question, the money reaching him is. So that direction takes the owner’s signature plus a received confirmation in his own app, and the code is not asked for. Neither mechanism covers both directions, which is why both exist.
Still open, and not drawn: an owner with no phone or no signal cannot read out a code. The honest fallback is an ops call, which needs a state on the line (verified_by: code | ops_call) and a person to answer the phone on a Friday evening — I have not designed it. Offline collection has the same gap: the device can queue a settlement, but it cannot verify a code it has never seen, so a queued collection is unverified until it syncs and that has to be visible to Karima.
